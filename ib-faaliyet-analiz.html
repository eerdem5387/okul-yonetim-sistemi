Sistem Ne Yapıyor?

Bu sistem, bir IB (International Baccalaureate) programı yürüten özel okula ait öğrenci faaliyet kayıt ve doğrulama sistemidir. Öğrencilerin katıldığı eğitim, etkinlik, spor ve yarışma faaliyetleri kaydedilir; her faaliyet için katılım kanıt fotoğrafı ve imzalı belge zorunludur. Onaylanan faaliyetler, harici IB gözlemcileri tarafından görüntülenebilir. PDF çıktıları (sertifika, başarı belgesi, müfredat) Puppeteer ile üretilir.

Temel Tasarım Kararları
✓ Tek Activity tablosu — faaliyet ve IB verisi ayrılmadı; category ve subtype alanlarıyla ayrım
✓ activityDate immutable — bir kez girildi mi asla değiştirilemez (API'de kasıtlı olarak atılıyor)
✓ Batch create — tek formda birden fazla öğrenciye aynı anda faaliyet eklenebilir
✓ IB Viewer izolasyonu — sadece isVerified:true kayıtlar görünür, ayrı token sistemi
! Auth localStorage'da — middleware yok; token'lar localStorage ile yönetiliyor
! Token formatı zayıf — role_staffId formatı, gerçek JWT değil

🔴 Kritik Sorunlar

Güvenlik
Token Formatı Güvensiz
Token formatı role_staffId (örn: admin_cm1abc123) gerçek bir JWT değil. Herhangi biri geçerli bir staffId bilirse doğrudan yetki taklidi yapabilir. Her API isteğinde DB sorgusu gitmesi kısmen hafifletiyor ama temel zafiyeti ortadan kaldırmıyor. → Çözüm: JWT + refresh token sistemi veya en azından HMAC imzalı token.
Güvenlik
IB Viewer Token URL'de Açık
PDF linkleri /api/ib/pdf/...?token=GERÇEK_TOKEN_DEĞERİ formatında. Bu token browser geçmişine, sunucu loglarına ve paylaşılan linklere düşer. → Çözüm: Token'ı URL'den kaldırıp Authorization header'a taşı veya kısa ömürlü, tek kullanımlık PDF token'ları üret.
Middleware Eksikliği
Sunucu Taraflı Route Koruması Yok
middleware.ts dosyası yoktur. Route koruması sadece client-side localStorage kontrolüne dayanır. JavaScript devre dışıyken veya direkt URL ile erişildiğinde sayfa render olabilir (API'ler 403 dönse de). → Çözüm: Next.js middleware ile cookie-based session veya SSR'de yetki kontrolü.

🟡 Teknik Borç / İyileştirme Gerektiren Alanlar

Veri Tutarsızlığı
Çift Doğrulama Alanı: isVerified + verificationStatus
Hem eski isVerified: Boolean hem yeni verificationStatus: Enum var. API'de senkron tutulmaya çalışılıyor ama bu karmaşıklık yaratıyor. IB Viewer filtresi isVerified: true kullanıyor; gelecekte tutarsızlık riski var. → Çözüm: isVerified'ı kaldır, sadece verificationStatus kullan. IB Viewer sorgusunu verificationStatus: "ONAYLANDI" olarak güncelle.
Legacy Enum
ActivityType Enum 14 Değerle Şişmiş — category/subtype ile Çakışıyor
Yeni sistem category + subtype kullanıyor ama eski ActivityType enum hâlâ var ve zorunlu. Config'de CATEGORY_TO_ACTIVITY_TYPE ve LEGACY_TYPE_TO_CATEGORY mapping'leri belirsizlik yaratıyor. Migration scripti var ama eski kayıtlar hâlâ karışık. → Çözüm: ActivityType'ı nullable yap veya 4 değerle sınırla; category/subtype'ı birincil yap.
Performans
Her İstekte DB Sorgusu ile Auth Doğrulama
Her API isteğinde prisma.staff.findUnique() çağrısı yapılıyor. Yoğun kullanımda N+1 sorununa benzer bir yük oluşturur. → Çözüm: Redis veya in-memory cache ile 5 dakikalık staff bilgisi cache'i. Veya gerçek JWT (DB sorgusu olmadan verify edilir).
UX
Onay Yetkisi Ayrımı Yok — Herkes Onaylayabiliyor
IB erişimi olan herkes (rehberlik dahil) başkasının faaliyetini onaylayabiliyor. "Kim onayladı" bilgisi verifiedBy alanında saklansa da enforce edilmiyor. Gerçek dünyada okul müdürü veya IB koordinatörü onaylamalı. → Çözüm: Onaylama yetkisini sadece belirli rollere (MUDUR, BAS_REHBERLIK) kısıtla.
UX
Silme İşleminde Onaylı Faaliyet Koruması Yok
ONAYLANDI durumundaki bir faaliyet bile silinebilir; sadece confirm() dialog'u var. IB programına raporlanmış bir faaliyet silinirse IB Viewer'da kaybolur. → Çözüm: ONAYLANDI durumdaki faaliyetlerin silinmesini engelle veya "arşivle" yerine "sil" mantığı getir.

🔵 Geliştirme Fırsatları

Feature
Bildirim Sistemi — Doğrulama Durumu Değiştiğinde
Şu an Notification modeli mevcut ama faaliyet doğrulama olaylarına bağlı değil. Faaliyet onaylandığında veya reddedildiğinde öğretmene/rehberliğe bildirim gönderilebilir.
Feature
Yıl/Dönem Bazlı Faaliyet Takibi
Şu an tarih filtresi var ama akademik yıla göre otomatik gruplama yok. AcademicYear modeli var; Activity'nin bir akademik yıla bağlanması IB raporlamayı kolaylaştırır.
Feature
Öğrenci Başına Min/Max Faaliyet Hedefi
IB programında öğrencilerin belirli kategorilerde minimum faaliyet sayısına ulaşması gerekebilir. Dashboard'a "hedef vs gerçekleşen" metriği eklenebilir.
Feature
Faaliyete Öğretmen / Danışman Yorumu
StudentComment modeli var ama Activity'e doğrudan bağlı değil. Bir faaliyete "bu öğrenci iyi performans gösterdi" gibi yorum eklenebilir.
